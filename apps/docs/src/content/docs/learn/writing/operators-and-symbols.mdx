Everything that computes in Dendrite is an **operator** (an **op**, for short): a named function
with named inputs, supplied by the standard library or by the application you are embedded in.
**Symbols** are a second way to spell the common ones.

```den
output sum  = 2 + 3
output same = Add(2, 3)
```

Those two lines are the same program. `+{:den}` is not built into the language: the standard
library registers it as sugar over its own `Add{:den}` op, and the parser rewrites it on the
way in. Nothing downstream can tell which spelling you used.

## Why that matters

Because it means there is no privileged arithmetic, and nothing to reverse-engineer when you go
looking for an op that should exist.

`>={:den}` is the clearest case. It has no op of its own:

```den inputs="n:number"
output a = $n >= 60
output b = Not(LessThan($n, 60))
```

Again, one program. If you go hunting for `GreaterThanOrEqual` in the
[standard library](../../../stdlib/) you will not find it, and now you know why. A symbol can
desugar into a whole little tree, not just a single call.

The practical upshot: **reach for the symbol when it reads better, the op when it reads
clearer.** `Add(price, tax, shipping){:den}` says "sum these three" better than a chain of
pluses, because `Add{:den}` is variadic and takes as many as you give it.

## The symbols, tightest binding last

| Symbols | Meaning | The op beneath |
| --- | --- | --- |
| `\|\|{:den}` | or, variadic | `Or{:den}` |
| `&&{:den}` | and, variadic | `And{:den}` |
| `=={:den}` `!={:den}` | equality | `Equals{:den}`, `NotEquals{:den}` |
| `<{:den}` `>{:den}` | comparison | `LessThan{:den}`, `GreaterThan{:den}` |
| `<={:den}` `>={:den}` | comparison | `Not(GreaterThan(…)){:den}`, `Not(LessThan(…)){:den}` |
| `+{:den}` `-{:den}` | addition | `Add{:den}` (variadic), `Subtract{:den}` |
| `*{:den}` `/{:den}` | multiplication | `Multiply{:den}` (variadic), `Divide{:den}` |
| `!{:den}` | not, prefix | `Not{:den}` |
| `-{:den}` | negate, prefix | `Negate{:den}` |

Multiplication binds tighter than addition, addition tighter than comparison, comparison tighter
than `&&{:den}`, and `&&{:den}` tighter than `||{:den}`: the ordering you already expect. Brackets
override it:

```den
output plain    = 2 + 3 * 4
output bracketed = (2 + 3) * 4
```

`plain{:den}` is 14 and `bracketed{:den}` is 20.

## Calling an op

An op's inputs have names, and you may pass them positionally or by name:

```den inputs="ready:boolean"
output positional = If($ready, "go", "wait")
output named      = If(condition: $ready, then: "go", else: "wait")
```

Named arguments cost more to type and pay for themselves on an op with three or four inputs, or
whenever the order is not obvious. The names are in the
[standard library reference](../../../stdlib/), which is generated from the ops themselves and so
cannot be out of date.

Two mistakes worth knowing by name. Pass an input an op does not have and you get
`unknown_op_input_key{:den}`, a warning: the value is ignored. Leave out one it needs and you
get `missing_op_input{:den}`, also a warning, with a default filled in for you, which is why a
half-written program keeps running while you write the rest of it.

## Text with holes

A template is text with expressions in it:

```den inputs="count:number, name:string"
output label  = `{$name} has {$count} left`
output nested = `outer {`inner {$count > 3}`}`
```

The backticks hold the text, and each `{…}` holds any expression, a template included. A hole is
`{…}` and not `${…}`, because `$` already means an input in this language: `${count}` is the text
`$` followed by the hole. Underneath, a template is a `Join{:den}` over its parts,
`Join([$name, " has ", $count, " left"]){:den}`, and `Join{:den}` converts each part to text itself,
so a number, a boolean, a null or a list in a hole needs no `ToString{:den}`. A template can span
lines, and `` \` `` and `\{` write a backtick or a brace as text.
